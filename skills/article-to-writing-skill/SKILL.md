# Article to Writing Skill

## 1. 目标与边界

把给定文章或文章集合，转化为一个可复用、可验证、可回滚的写作 Skill。核心闭环是：

`样本观察 → 证据台账 → 最小 Skill → 测试提示 → 基线重写 → 独立评分 → 只修最低维度 → 回归验证 → 接受或回滚`

这里的“自进化”是受约束的 hill-climbing，不是无记录的自我改写：每轮只允许一个可解释的规则变化，只有客观分数改善且没有明显副作用时才晋级。

不要把文章里的主题事实、人物、数字、独特比喻、固定署名或一句话金句写进通用 Skill。Skill 提炼的是写作机制、决策顺序、语气旋钮和适用边界。

## 2. 何时使用

使用本 Skill 的典型请求：

- “根据这几篇文章提炼作者写作风格/写作 Skill”；
- “把这篇文章的方法沉淀成一个可复用的 SKILL.md”；
- “用提炼出的 Skill 重写原文，和原文对比打分，不通过就继续优化”；
- “评估现有写作 Skill 是否过拟合，并用新文章做回归”；
- “从一篇 PDF、公众号文章、专栏、品牌稿或个人写作样本中抽象方法论”。

不把以下内容当作可直接迁移的写作规则：未经授权的身份与客户信息、未核验的事实、来源作者的独特连续表达、单篇文章的具体产品结论，以及为了模仿而复制的句子。

不适合直接触发：没有任何源文、只要求从零写一篇普通文章；只要求做事实/法律/医学审查而不提炼写作机制；或明确要求抄袭、冒充来源作者、伪造原始记录。

## 3. 输入契约与工作模式

先确认并记录：

- 样本文件、数量、格式和是否能读取全文；PDF 需要同时抽查页面视觉结构，不能只依赖 OCR；
- 目标任务：仿写、改稿、内容生产、品牌统一，还是仅做风格研究；
- 目标读者、发布渠道、语言、长度和必须保留的事实；
- 来源文章的使用授权、作者身份和隐私边界；没有授权时只提炼抽象机制，不替来源作者发声；
- 用户希望的输出位置。未指定时，在当前工作区建立独立 Skill 目录，不覆盖现有 Skill。

按样本量选择模式：

| 模式 | 做法 | 结论边界 |
|---|---|---|
| 单篇校准 | 从一篇文章提炼假设，重写同题文章并盲评 | 只能称为“初步/暂定规则”，不能宣称泛化 |
| 多篇提炼 | 先找跨文章重复机制，再按题材分组 | 可把重复机制提升为候选核心规则 |
| 现有 Skill 进化 | 读取旧 Skill、回归样本、评分日志，单轮只改一个维度 | 必须保留可回滚版本和变化记录 |
| 仅评估 | 生成测试提示和评分卡，不改 Skill | 先展示测试范围与评分口径 |

样本少于 3 篇时，默认把所有新规则标记为 `provisional`；至少 3 篇且覆盖 2 种题型后，才允许讨论跨题材泛化。单篇结果默认不能生成可被 Codex 自动发现的 `SKILL.md`，只能生成隔离的 `calibration/draft-SKILL.md`；用户明确确认要做实验性加载时，也必须标注为 sandbox-only。

把评估任务分成两种并在测试提示中标注：`same-task` 是保留同一写作目的的改写，用来校准源文机制；`transfer` 是把候选规则迁移到新题型或新材料，用来检查泛化。单篇的 `transfer` 只能算迁移压力测试，不能替代第二篇独立作者文章的验证。

## 4. Phase 0：建立可追溯工作区

将工作分为三个层次，避免把源材料和通用规则混在一起：

```text
<skill-dir>/
├── SKILL.md                         # 只放核心流程与触发描述
├── agents/openai.yaml               # 推荐：为生成的 Skill 提供 UI 元数据
├── references/style-profile.md      # 观察到的稳定机制与条件规则
├── references/evaluation-rubric.md  # 评分维度、门槛和自动失败项
├── evals/test-prompts.json          # 测试输入与期望行为
├── reports/evolution-report.md      # 每轮诊断、变化和结果
└── results.tsv                      # 可选的机器可读评分日志
```

若环境有 git，先创建工作分支并记录基线；没有 git 时，用带时间戳的备份保存上一版。绝不使用破坏性 reset 覆盖用户已有改动。

在正式评估前先设计 2—3 个测试提示：至少一个典型场景、一个不同题型或更复杂场景；若用户只给一篇文章，测试提示必须覆盖同一机制的不同表达，不能只换名词。

测试提示必须先展示给用户确认，除非用户已经明确授权自动完成整个闭环。提示中只写任务和输入材料，不泄露期望答案、诊断结论或准备修复的规则。

## 5. Phase 1：从文章提炼证据，不急着写规则

### 5.1 先做文章地图

逐篇记录以下事实，使用短语和转述，不复制长段落：

1. 文章任务：解释、说服、复盘、叙事、建信任、销售转化或其他；
2. 读者问题与核心冲突：读者起初相信什么，作者让其改变了什么判断；
3. 结构因果：事件/问题如何进入，作者做了什么，哪条证据改变了决策，结尾如何收束；
4. 语言行为：人称、句长、段落节奏、问答、反问、术语解释和视觉重音；
5. 证据与场景：数字、对话、物件、动作、情绪和生活后果分别承担什么功能；
6. 交易与安全：哪些事实必须保留，哪些内容只能转述、泛化或删除。

### 5.2 建立规则证据台账

每条候选规则都要有来源和范围，并把台账保存为独立的 `reports/evidence-ledger.md`，不能只留在临时推理中：

| 字段 | 要求 |
|---|---|
| rule_id | 稳定编号，例如 `R-STRUCT-01` |
| observation | 可观察的写作动作，不写空泛形容词 |
| evidence | 来源文件、页码/段落和不超过必要长度的短语 |
| scope | `core`、题型条件、单篇偶然或安全约束 |
| confidence | 高/中/低，并说明依据 |
| effect | 它改变读者理解、情绪、信任还是行动 |
| negative_case | 哪些文章没有它，防止把缺席误判为硬规则 |
| action | 写入 Skill、放进 reference，或暂不迁移 |

把观察分成四类：

- `invariant`：跨多篇、跨题型重复，才可候选为核心规则；
- `conditional`：只在某种题型、渠道或目标下有效，放入模块；
- `incidental`：单篇数字、人物、金句、章节数或视觉习惯，不升级；
- `safety`：授权、隐私、版权、事实和合规要求，独立于作者风格管理。

不要用“像不像作者”作为唯一观察。把规则写成可执行动作，例如“先呈现读者的具体疑问，再给方向性判断”，而不是“要有作者感”。

## 6. Phase 2：生成最小可用 Skill

先写一个能完成任务的最小版本，再加入经过验证的例外。核心 `SKILL.md` 必须包含：

1. frontmatter 中清楚写明“做什么”和“何时触发”；
2. 输入检查与授权/版权边界；
3. 文章模式选择或题材路由；
4. 从材料到草稿的线性工作流；
5. 事实、引语、数字和推断的证据门槛；
6. 默认输出和失败时的报告格式；
7. 评分、回归、接受和回滚规则；
8. 指向 references 的“何时读取”说明。

将详细画像、长例子、评分表和题型模块放入 references，保持核心 `SKILL.md` 少于 500 行。单篇校准时，先写隔离的 `calibration/draft-SKILL.md`，不得把暂定规则放到目标 Skill 根目录。不要为了满足样本数量，强迫每篇文章使用相同的开头、编号、小标题、数字、反问、CTA 或免责声明。

### 6.1 规则晋级条件

在没有重复证据时，规则只能进入校准报告，不能进入核心 Skill：

- 至少 3 篇、覆盖至少 2 种题型重复出现，或用户明确指定为品牌硬要求：可进入 `core`；
- 只在同一题型中重复：进入题型模块，并写明适用条件；
- 只出现一次：保留为 `incidental`，不得作为配额或硬门槛；
- 与事实、身份、授权有关：进入 `safety`，不能伪装成风格特征。

如果只有一篇文章，允许做“机制假设 → 同文重写”的校准，但报告必须写明：尚未证明跨文章泛化。

## 7. Phase 3：基线、重写与独立评分

### 7.1 先固定评分口径

在看到重写结果前，确定评分维度、权重、通过线和自动失败项。默认使用 100 分卡，具体标准见 `references/evaluation-rubric.md`：

- 任务与读者适配 15；
- 结构与因果推进 15；
- 语言、声音与节奏 15；
- 说理机制与证据功能 15；
- 场景/情绪/作者在场保真 10；
- 价值交付与行动收束 10；
- 泛化与表层自由度 10；
- 原创、版权与安全 10。

评分的是机制和读者效果，不是字面相似度。对“来源保真”和“原创安全”分别评分，不能用复制原文换高分。

单篇候选稿的分数只说明这一次重写是否合格；Skill 是否有效，要看多个测试提示的聚合分数和留出集表现。没有留出集时，不把单篇高分写成 Skill 已验证。

### 7.2 做两种比较

对每个测试提示，尽量保留三份材料：

1. `source`：作者原文或由用户提供的事实基线；
2. `baseline`：不加载新 Skill 的普通完成稿；
3. `candidate`：加载当前候选 Skill 的完成稿。

比较时回答：候选稿是否比 baseline 更好地完成任务？是否保留了原文的结构机制、声音和关键场景？是否引入了模板化、虚构、过度冗长或版权风险？

同时区分两种评分：过程评分检查是否完成了文章地图、证据台账、测试设计和进化日志；输出评分检查 baseline/candidate 的文章质量。只有输出评分在多个提示和留出集上改善，才能说明候选 Skill 有效。

有条件时使用独立子 agent 或另一轮盲评：评审只接收源文、用户任务和两份匿名输出，不接收你的诊断与预期修复。没有子 agent 时可以干跑，但必须在报告中标记 `eval_mode: dry_run`，不能把干跑当成实测。

## 8. Phase 4：受控自进化循环

默认最多 3 轮；每轮严格执行：

```text
诊断最低分维度
→ 提出一个具体规则变化
→ 只修改该维度相关的 Skill 内容
→ 用同一测试集重写并评分
→ 检查 holdout、自动失败项和模板坍缩
→ 分数严格提升且无明显副作用则 keep，否则 revert
```

每轮必须记录：改了哪条规则、基于哪些证据、预期提升、实际分数变化、是否影响其他题型、keep/revert 及原因。

不得用以下方式制造“高分”：

- 为某篇文章新增人物、金额、句子或事实；
- 把评分者指出的一个句子硬编码为通用模板；
- 只增加免责声明、CTA 或编号来掩盖结构问题；
- 同时改多个维度，导致无法知道什么产生了效果；
- 让验证样本参与规则提炼后，再声称它证明了泛化。

如果连续两轮最低维度没有改善，停止局部加规则，报告瓶颈；只有在用户确认后才做一次探索性重写。探索性重写也必须与当前最佳版本比较，失败则恢复最佳版本。

## 9. Phase 5：回归、防过拟合与停止条件

### 9.1 回归设计

- 3 篇以上：至少覆盖 2 种题型；
- 5 篇以上：优先使用训练集/留出集，不能只在原文上自测；
- 文章数量不足：把结果标记为校准，不写“泛化已验证”；
- 不同题型应允许不同结构，检查家庭故事是否被改成清单、服务文章是否被改成广告、概念文是否被强行塞进人物故事；
- 对每篇记录“原文有/候选稿有/Skill 强制添加”的表层特征，三类差异过大时判为模板坍缩风险。

### 9.2 通过与停止

默认通过条件：无自动失败项，总分至少 85/100，且结构、声音、泛化三个维度不能明显低于其他维度。对单篇样本，即使分数通过，也只能标记 `provisional`。

遇到以下情况立即暂停，不继续用文风掩盖问题：源文不可读、授权不明、关键事实无法核验、候选稿新增不可追溯引语/数字、出现版权或身份冒充风险、验证集明显退化。

达到门槛、连续两轮无实质提升，或已经证明新增规则只对单篇有效时停止。停止不是失败；报告剩余不确定性比继续堆模板更有价值。

## 10. 交付格式

默认交付以下内容，按用户要求删减；单篇校准使用 `calibration/` 隔离目录，达到多篇晋级门槛后才提升到 Skill 根目录：

1. 已验证时交付可直接使用的 `SKILL.md`；单篇时交付不可自动加载的 `calibration/draft-SKILL.md`；
2. `references/style-profile.md`：稳定规则、题型条件和证据范围；
3. `references/evaluation-rubric.md`：评分维度、权重、门槛和自动失败项；
4. `evals/test-prompts.json`：测试提示、输入范围和期望行为，不写答案；
5. `reports/evidence-ledger.md`：逐条规则的证据、范围、反例和晋级状态；
6. `reports/evolution-report.md`：基线、每轮改动、分数、keep/revert、泛化结论和遗留风险；
7. 已验证 Skill 的 `agents/openai.yaml`；单篇 provisional 不生成可发现的 UI 元数据；
8. 可选 `results.tsv`：机器可读的分数历史。

报告第一行写：

`状态：已验证 / 暂定（单篇校准） / 暂停（待授权、待事实、待测试或待用户确认）`

## 11. 异常处理

- 只有一篇文章：生成暂定 Skill 和第二篇测试建议，不把单篇特征写成核心规则；
- PDF/OCR 不完整：标记不可见段落，不猜测缺失文字；需要视觉判断时先读取 PDF 相关 Skill；
- 没有原始对话或数据：使用转述/假设并标记来源，不补造引语；
- 没有 git：创建可恢复备份，报告无法执行 commit/revert；
- 子 agent 不可用：执行 dry run，降低“实测效果”置信度；
- 评分提升但 holdout 下降：拒绝该修改，优先保留泛化更好的版本；
- 用户要求只读评估：不创建、覆盖或回滚文件，只返回证据台账、测试提示、评分卡和建议变更；
- 用户只要 Skill 不要文章：交付规则和验证资产，不擅自生成完整仿写稿。
- 用户要求单篇结果直接上线：说明这是同文校准，要求第二篇独立文章迁移测试；未通过前不把 `draft-SKILL.md` 改名为可加载的 `SKILL.md`。

## 12. 快速自检

- 是否把“观察”与“规则”分开，并为每条核心规则保留证据？
- 是否把单篇事实、金句、数字、人物和视觉习惯排除在核心 Skill 外？
- 是否先固定评分口径，再看候选稿？
- 是否有 baseline、candidate 和至少一个不同题型/留出样本？
- 每轮是否只改一个维度，并保留 keep/revert 记录？
- 是否同时检查原创安全、事实追溯、授权和模板坍缩？
- Skill 本体是否少于 500 行，长资料是否放在直接引用的 references？
- 最终报告是否诚实区分实测、dry run、单篇暂定和跨文章验证？

评分细则和台账模板见：

- `references/evidence-and-scope.md`：证据台账、规则晋级和防过拟合；
- `references/evaluation-rubric.md`：评分卡、测试提示和进化日志格式。
