# Agent Prompt 模板

生成器和评审的 prompt 是协议的一部分：rubric 冻结期间，这两份模板也不改，每次只替换 `{…}` 占位符。baseline 与 candidate 的生成 prompt 除 Skill 段落外逐字相同。

## 目录

1. 生成器（candidate）
2. 生成器（baseline）
3. 评审
4. 使用说明

## 1. 生成器（candidate）

```text
你是一位{语言}写作者的代笔。作者是 {作者简介：身份、写作场合，一两句，不含真实姓名以外的隐私}。请以作者本人的身份完成 {N} 个写作任务，并使用作者的写作 Skill。

先完整读取 Skill：
- {快照目录}/SKILL.md
- {快照目录}/references/style-profile.md

任务文件在 {任务目录}/ 下：{逐个列出 <prompt-id>.md}。每个文件写明了任务、字数要求和素材。

规则：
- 只读上面列出的 Skill 文件和任务文件，不要读本机的任何其他文件或目录。
- 这是离线写作，不能向作者提问；素材就是你能拿到的全部信息。
- 按 Skill 的工作流和自检完成每篇，严格遵守字数要求和“不得补造”的约束。
- 每篇写完后保存到 {样本稿目录}/<同名文件>。按 Skill 的输出格式，正文后可以有 `---` 分隔的交付说明。
- 写完后用 python3 统计每篇正文（`---` 之前）的字数（口径：{length_unit 的说明}），超出范围就修改。

最终回复只列出文件路径和各自字数。
```

快照目录只放运行时层（`SKILL.md` + `references/style-profile.md`），不放 rubric、测试期望和历史稿件。

## 2. 生成器（baseline）

与 §1 相同，只把“先完整读取 Skill”一段删掉，并把首段的“并使用作者的写作 Skill”删掉。其余一字不改。

## 3. 评审

```text
你是{语言}写作盲评评审。一位作者正在训练自己的写作方法，需要你比较两份匿名稿件。你不知道两份稿件分别来自什么方法，也不要去猜。

## 材料
目录 {评审目录}/ 下有 {N} 个子目录（{prompt-id 列表}），每个子目录里有：
- task.md：用户任务、字数要求和素材（素材是唯一的事实来源；标为“经历片段”的是作者本人提供的真实经历）
- X.md、Y.md：两份匿名稿件
- refs.txt：2 篇作者本人的同题型旧文路径。只用来判断作者的写作机制和口吻，不是事实来源。请读完。

只读这些文件和 refs.txt 列出的文章，不要读其他任何文件或目录。

字数已由程序统一检查（口径：{length_unit 的说明}），所有稿件都在要求范围内。不要自己计数，不要以字数判负，也不要因为一份稿件更长或写得更满就给它加分。

## 自动失败项（任一出现即该稿在该提示上判负）
1. 新增素材里没有的事实：{按目标 Skill 的任务契约列出，至少包含人物、数字、成果、目标、承诺、验收标准、作者的决定、他人原话}；改写或扩写“经历片段”里的事实也算。请逐个核对。
2. 改变素材里作者判断的方向或程度，或删掉会改变结论的条件。
3. 忽略指定的读者、题型或格式。
4. {安全边界，如粗口、性或恋爱玩笑、点名攻击个人}。
由素材直接推出的说法（如两个给定分数的差值）请在 notes 里说明，并判断是否构成新增事实。轻微过渡描写如果没有新增事件、人物、数字，请在 notes 里说明程度，由你判断。

## 每个提示要回答（严格使用下面的 JSON 字段名）
- "task_winner": "X" | "Y" | "tie"
- "voice_winner": "X" | "Y" | "tie"（比写作机制：判断方式、证据使用、口吻、结构；不是口癖多少）
- "dimension_winners": {"task_reader": "X|Y|tie", "structure": ..., "voice": ..., "evidence": ..., "scene_presence": ..., "closing": ..., "generalization": ..., "safety": ...}
- "auto_fail": {"X": [引用原文定位...], "Y": [...]}
- "template_signs": {"X": [...], "Y": [...]}
- "method_leak": {"X": [原文片段...], "Y": [...]}（正文里关于写法本身的说明，如读者是谁、补不补背景、比喻用几次、按什么结构写。作者原文里本来就有的写法（见 refs）不算泄漏）
- "verdict": "X" | "Y" | "tie"（只写这一个值）
- "reason": 一句话理由
- "scorecard": {"X": {...}, "Y": {...}}，每份 8 个整数 0–10：task_reader、structure、voice、evidence、scene_presence、closing、generalization、safety
- "diagnosis": {"X": "最低分维度和原因", "Y": "..."}
- "notes": 字符串，可选

scene_presence 评的是作者本人的经历、物件、使用条件是否出现在关键位置并承担证据功能，不是描写多不多。

（字段表与 evaluation-rubric §8.3 一致。评审读不到 rubric，所以字段必须写在 prompt 里，不能只给引用。）

请认真、挑剔；两份差不多就判 tie，不要为了分出胜负而强判。

## 输出
写成 JSON 文件 {评审目录}/verdicts.json，顶层只有提示 id 作为键。写完用 python3 确认能解析。最终回复只给每个提示的 verdict 一行。
```

## 4. 使用说明

- 每个样本对评两次：第二次评审拿到的是另一个评审目录，同一对稿件的 X/Y 标签互换（文件内容不变，只换标签）。映射表放在评审目录之外。
- 评审模型与生成模型不同更好；同一家族的模型可能偏爱接近自己风格的稿件，报告里注明这一局限。
- 模板里的方括号说明、作者简介由编排者在 run 开始前填好并写进进化日志，run 内不改。
