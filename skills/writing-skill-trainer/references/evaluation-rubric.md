## 1. 自动失败项

任一项出现，当前候选版本不得晋级：

- 编造源文没有支持的人物、事实、引语、数字或经历，包括替作者新增目标、承诺、验收标准或决定（如“我不会买”）；
- 复制来源的独特连续表达、固定署名，或让读者误以为来源作者亲自发布；
- 把单篇事实、产品结论、人物细节或视觉配额写成所有文章都必须遵守的规则；
- 忽略用户指定的任务、读者、渠道或输出格式；
- 为追求风格分数删除会改变结论的条件，或把不确定内容写成确定事实；
- 授权、隐私、版权或关键事实存在明确阻断，却把结果标记为可发布/已验证。

自动失败项优先于总分。增加免责声明不能修复核心事实、结构或版权错误。

## 2. 默认评分卡

先按每项 0—10 评分，再乘以权重：

| 维度 | 权重 | 主要问题 |
|---|---:|---|
| 任务与读者适配 | 15 | 是否完成用户目的，是否对目标读者有效 |
| 结构与因果推进 | 15 | 事件、问题、证据、转折和结论是否相互推动 |
| 语言、声音与节奏 | 15 | 人称、句长、口语度、密度和声音是否可辨 |
| 说理机制与证据功能 | 15 | 类比、数字、对话、细节是否承担清楚的论证功能 |
| 场景、情绪与作者在场 | 10 | 有证据的生活后果、观察和服务动作是否被保留 |
| 价值交付与行动收束 | 10 | 是否让读者获得判断，结尾是否与任务自然相连 |
| 泛化与表层自由度 | 10 | 能否适配其他题型，是否避免固定模板坍缩；正文是否泄漏 Skill 的方法用语（如“回指”“这个比喻我只用一次”） |
| 原创、事实与安全 | 10 | 是否可追溯、不过度复制、不冒充且边界清楚 |

总分：

`总分 = Σ（维度得分 ÷ 10 × 权重）`

默认门槛：无自动失败项、总分 ≥85；跨文章验证时，“泛化与表层自由度”不得低于 7/10；单篇只能标记 `provisional`，不能因为高分宣称泛化。门槛只用于最终通过判定；每轮 keep/revert 用 §3.5 的成对比较裁决，不比较绝对分数。

## 3. 评分解释

### 3.1 0—3：失败

任务偏离、结构断裂、声音完全泛化、证据失真，或有明显安全问题。

### 3.2 4—6：可读但不稳定

部分机制出现，但依赖模板、解释悬空、场景被削弱，或只在源文上有效。

### 3.3 7—8：合格

主要机制被保留，候选稿完成任务，局部仍需精修；规则有条件且可解释。

### 3.4 9—10：稳定

候选稿既保留底层功能又保留表层自由度；跨题型仍有效，且没有以复制或虚构换取相似感。

评分时同时写三句话：

1. 最高分维度的具体证据；
2. 最低分维度和造成失分的一个原因；
3. 下一轮只应改变哪一条规则。

### 3.5 评分卡诊断，成对比较裁决

单次 LLM 绝对打分噪声通常在 ±1 分以上，1—2 分的总分差异大概率是噪声。因此：

- 评分卡只用于**诊断**：定位最低分维度，决定下一轮改什么；
- keep/revert 用**盲评成对比较**裁决：评审接收源文、用户任务和两份匿名稿件（不知道哪份是新版本），回答哪份更好完成任务、是否保留机制与声音、是否引入模板化/虚构/版权风险；
- 候选稿不必在每一项都高于 baseline；若在源文上胜出、在留出集下降，判定为过拟合，拒绝该修改。

### 3.6 比较对象与裁决口径

两种比较必须分开，口径在生成候选稿之前写进进化日志：

| 比较 | 何时 | 默认 keep 口径 |
|---|---|---|
| 候选 v1 vs baseline（不加载 Skill） | 只做一次，作为“Skill 是否有用”的门槛 | 多数提示 win，且留出提示不 lose |
| 第 N 轮 vs 当前最佳版本 | 每轮一次 | 全部样本对合计净胜 ≥ 0；没有任何提示两对都 lose；留出提示合计净胜 ≥ 0；本轮目标按事先写定的指标改善（见下） |

单条规则的改动通常只影响一两个提示，因此每轮不要求“多数 win”，否则合理的定点修复永远无法晋级。也不用“任何提示都不 lose”：每提示只有 2 对样本时，零差异下单提示 lose 的概率约 31%，3 个提示全不 lose 只有约 33%，一条无害的改动多半会被误判 revert。上表口径在零差异下的通过率约 50%，同时仍能拦住单个提示上的明确退化（两对都 lose）。

“目标改善”必须事先写成可计数的指标，不用评分卡绝对分：
- 目标是编造、泄漏等失误：按稿件计数（自动失败稿数、泄漏处数），候选少于当前最佳；
- 目标是某个质量维度：用评审 JSON 的 `dimension_winners`，该维度在全部样本对上 win 多于 lose。

不做事后豁免。改动前在日志里写明“预期受影响的提示 id”；未列入的提示出现单对 lose，记为生成波动，不计入裁决，但两对都 lose 仍按上表处理。

### 3.7 胜因分类

每个 win 记录胜因：`quality`（候选稿本身更好）或 `opponent_fail`（对手触发自动失败）。报告分别统计两类胜场；主要靠 `opponent_fail` 取胜时，不能说明 Skill 提升了写作质量，只能说明它减少了失误。

### 3.8 噪声底与评审可靠性

裁决前先知道这套评审能分辨多大的差异：

- **交换顺序不一致率**：同一样本对的两次评审结论相反（一次 X、一次 Y）的比例。超过约 40% 时，本轮差异多半在噪声以下，或评审有位置偏差，结论降级为“不确定”。
- **A/A 对照**（每个 run 一次，2 个评审 agent）：拿当前最佳版本的两份样本互评。A/A 里非 tie 的比例就是噪声底；候选的净胜幅度不超过它，就不能说明改动有效。
- **不区分的提示**：一个 run 里所有样本对都是 tie 的提示，标为“不区分”，下个 run 替换或加难。
- **正负对照**（可选，每个 run 一次）：让评审比较留出原文和 baseline 稿。评审若不能稳定判原文更像作者，说明口吻判断不可信，先修评审 prompt 或参考文章。
- **作者校准**：v1 vs baseline 之后和 run 结束时，各从已评的样本对中抽 2—3 对，同样以 X/Y 匿名的形式请作者选“哪篇更像我”，记录评审与作者的一致率。不一致的案例记入裁判审计日志（§7）。写作风格类任务的真值是作者本人，这一步只花作者几分钟，不增加子 agent。

## 4. 测试提示模板

保存为 `evals/test-prompts.json`。`expected` 只写可观察行为，不写答案：

```json
[
  {
    "id": "happy-path-01",
    "type": "same-task",
    "holdout": true,
    "holdout_source": "corpus/holdout/sample-a.md",
    "length": [1000, 1400],
    "length_unit": "nonspace",
    "task": "根据给定素材写一篇同主题文章；只能使用素材中的事实和判断。",
    "materials": ["事实 1", "作者判断 1", "经历片段：作者口述的一个真实时刻"],
    "expected": "完成用户任务，保留核心结构机制，输出原创且可追溯的稿件。"
  },
  {
    "id": "transfer-01",
    "type": "transfer",
    "holdout": false,
    "length": [900, 1200],
    "length_unit": "nonspace",
    "task": "将同一写作机制用于不同题型，允许改变开头、结构和结尾形式。",
    "materials": ["……"],
    "expected": "迁移底层机制，不强行复制源文表层模板。"
  }
]
```

字段约定：

- `length_unit` 必填，取值见 `scripts/precheck.py`：`nonspace`（去空白后全部字符，含英文和数字，中文默认）、`cjk_punct`（汉字加全角标点）、`words`（英文词数）。字数只由脚本计算，评审不自行计数。
- `materials` 是唯一事实来源。只给结论、不给经历的素材，会让“场景与作者在场”维度在“不得补造”约束下无法提升；需要测这一维度时，至少一个提示应包含作者提供的真实经历片段（见 SKILL.md §7.1 素材追问）。
- `length` 的下限要和素材体量匹配。设计完提示后自己估一下：只用素材、不加任何新事实，能写到多少字？明显不到下限就降下限或补素材。下限高于素材体量时，写手会扩写经历、补感想句，评审随后判出的编造是测试设计诱导的。
- 交给生成器的任务文件只包含 `task`、`length`、`materials`，不包含 `expected` 和 `holdout_source`。

至少包含一个 `same-task` 典型提示和一个 `transfer` 迁移/复杂提示。单篇样本的 `transfer` 只能标记为压力测试，不得作为独立文章泛化证据。测试提示默认展示给用户后继续执行；仅当用户要求逐步确认时才停在测试设计阶段（SKILL.md §5）。

## 5. 进化日志

`reports/results.tsv` 可使用以下表头：

```tsv
timestamp	run_id	version	compared_to	prompt_id	pairwise_result	win_basis	lowest_dimension	prediction_hit	status	eval_mode	note
```

`status` 使用 `baseline`、`keep`、`revert`、`blocked`；`eval_mode` 使用 `full_test` 或 `dry_run`；`pairwise_result` 使用 `win`、`lose`、`tie`；`win_basis` 使用 `quality`、`opponent_fail` 或 `-`（见 §3.7）；`compared_to` 写对比版本（`baseline` 或当前最佳版本号）；`prediction_hit` 使用 `yes`、`no`（预期改善的维度是否真的改善）。按 §3.6 的口径写 `keep`。

每轮改动记录格式：

```text
假设：把规则 R-STRUCT-02 改为条件规则，能减少家庭故事的模板化。
证据：sample-a 第3段、sample-c 结尾；sample-b 没有该特征。
变更：只调整题型路由，不新增固定小标题。
预期：泛化维度改善，源文声音不下降。
结果：盲评 candidate 胜出（2/3 提示）；holdout 未退化；预测命中；决定 keep。
```

连续两轮 `prediction_hit: no` 时触发预测校准停机（见 SKILL.md §9.1）：停止爬山，回到证据提炼阶段重新诊断。

## 7. 裁判审计日志

rubric 在单个 run 内冻结；本节格式用于 run 之间的外环审计（见 SKILL.md §9.3）。

发现"评分结论与用户实际判断相悖"的案例时，追加一行到 `reports/rubric-audit.md`：

```text
案例：candidate v3 总分 88 通过，用户判断"模板感重、不像作者"。
指向缺陷：泛化与表层自由度维度未捕捉到小标题句式趋同。
状态：待累积（1/2）。
```

同一缺陷累积 2 个以上案例后，才允许在下一个 run 开始前修改一次 rubric；修改记录追加：

```text
变更：泛化维度评分问题中加入"连续小节句式是否趋同"检查项。
依据：案例 #1、#3。
版本：rubric v2（v1 保留于 git 历史或备份）。
```

进化循环进行中不得修改 rubric。

## 8. 机械预检与盲评协议

### 8.1 机械预检

评审前对每份稿件运行：

```bash
python3 -I <trainer>/scripts/precheck.py --prompts <skill-dir>/evals/test-prompts.json \
  --corpus <训练语料目录> <baseline 稿目录> <candidate 稿目录>
```

每个样本一个稿目录（如 `v2/s1/`、`v2/s2/`），目录内文件名必须是 `<prompt-id>.md`；文件名对不上提示 id 或目录里没有可检查的稿件时，脚本以退出码 2 报错而不是跳过。脚本检查字数（按 `length_unit`，容差 ±10%）、素材外的数字和书名、与训练语料 ≥12 字的连续重合。退出码非 0 时，先逐条核对：由素材推出的数字（如两个分数的差值）交给评审判断；真正的新增事实直接记为该稿的自动失败。评审说明中写明“字数已由程序检查，不要自行计数”。

已知盲区（脚本通过不等于没有编造，评审仍要逐项核对）：
- 数字按子串匹配：素材有 `2015` 时，稿件新增的 `5` 不会报出；中文数字（“三千块”）不检测。
- 交付说明按独占一行的 `---` 截断：正文中间若有 `---` 分隔线，后文会被当作交付说明丢掉，字数会被误判为不足。目标 Skill 的正文里不要用 `---` 作分隔线。
- `corpus_overlap` 只报告、不影响退出码，命中后由评审判断。
- 字数不足但交付说明里声明了“素材只够这些字”的稿件：编排者核对声明是否属实（素材确实撑不到下限）。属实就不记字数失败，并回到 §4 检查测试提示的下限设计；不属实，重生成一次，仍不过记该稿自动失败。

### 8.2 盲评材料准备

1. 去掉稿件末尾的交付说明（`---` 之后的内容），避免评审从格式认出加载了 Skill 的一方。
2. 每个提示随机分配 X/Y，评两次，第二次交换顺序；映射表放在评审被告知不得读取的目录（如 `judge-secret/`）。
3. 每个提示目录只放：任务文件、X、Y、作者同题型参考文章路径。留出原文可以作为评审的口吻参考，但**生成器永远不能读取留出集**。
4. 评审 prompt 用 `references/agent-prompts.md` 的固定模板，写明只读该目录；评审模型与生成模型不同更好。
5. 两次评审结论不一致记为 `tie`；任一次评审判定某稿触发自动失败，且复核成立，该稿在该样本对上记 `lose`。
6. **多样本配对**：每个版本每个提示至少 2 个样本（`a1, a2` 与 `b1, b2`，各来自独立的生成 agent）。按编号配对（`a1–b1`、`a2–b2`），每对照第 2—5 条各评两次。不先挑“较好的一篇”，挑选本身需要评审，还会引入偏差。
7. **合并到提示**：两对结果按 win=+1、tie=0、lose=−1 相加，和 >0 记 win，<0 记 lose，=0 记 tie。results.tsv 每对一行（`note` 写样本编号），再加一行合并结果。
8. 自动失败另按稿件计数：每个版本报告“自动失败稿数 / 总稿数”。目标问题是编造或泄漏时，用这个比例判断是否改善，不只看胜负。

### 8.3 评审输出 schema

要求评审写成 JSON，顶层只有提示 id，便于程序揭盲：

```json
{
  "<prompt-id>": {
    "task_winner": "X | Y | tie",
    "voice_winner": "X | Y | tie",
    "auto_fail": {"X": ["引用原文定位"], "Y": []},
    "template_signs": {"X": [], "Y": []},
    "dimension_winners": {"task_reader": "X | Y | tie", "structure": "...", "voice": "...", "evidence": "...", "scene_presence": "...", "closing": "...", "generalization": "...", "safety": "..."},
    "method_leak": {"X": ["正文里关于写法本身的说明"], "Y": []},
    "verdict": "X | Y | tie",
    "reason": "一句话理由",
    "scorecard": {"X": {"task_reader": 0, "structure": 0, "voice": 0, "evidence": 0, "scene_presence": 0, "closing": 0, "generalization": 0, "safety": 0}, "Y": {}},
    "diagnosis": {"X": "最低分维度和原因", "Y": "..."},
    "notes": "可选"
  }
}
```

`verdict` 等字段只写枚举值，理由放在 `reason`；否则揭盲脚本无法可靠解析。`dimension_winners` 是按维度的成对结论，用于判定目标维度是否改善（§3.6）；`scorecard` 绝对分只作诊断。评审 prompt 用 `references/agent-prompts.md` 的固定模板，只替换路径，rubric 冻结期间模板也不改。

### 8.4 成本预估

按每版本每提示 2 个样本计：每轮约 2 个生成 agent（候选）+ 4 个评审 agent（2 对 × 交换顺序；同一评审可在一个 agent 里评完一对的所有提示）；对照版本已有同提示、同 Skill 的 2 个样本时可复用，否则再加 2 个生成 agent。v1 vs baseline 一轮约 8 个。默认最多 3 轮（含 v1 vs baseline），另加 A/A 对照 2 个评审 agent（§3.8），一个完整 run 约 17—22 个子 agent。作者校准不占子 agent。开跑前告知用户。
