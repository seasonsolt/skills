# Writing Skill Trainer

## 1. 目标与核心闭环

把给定文章或文章集合，转化为一个可复用、可验证、可回滚的写作 Skill。全流程闭环：

`样本观察 → 证据台账 → 最小 Skill → 测试提示 → 基线重写 → 盲评比较 → 只修最低维度 → 回归验证 → 接受或回滚`

这里的"自进化"是受约束的 hill-climbing：每轮只允许一个可解释的规则变化，盲评不输于当前最佳版本、目标问题改善且无副作用才晋级。改进对象分两层——内环迭代候选 Skill（按轮），外环审计评分标准本身（按 run，见 §9.3）；两层永远不在同一轮内同时改动。

## 2. 硬约束

以下规则贯穿全流程，只在此处完整陈述一次：

1. **单篇即暂定**：样本少于 3 篇时，所有新规则标记 `provisional`；产物放入隔离的 `calibration/` 目录（`draft-SKILL.md`），不生成可被自动发现加载的 `SKILL.md`，不生成 UI 元数据。达到多篇晋级门槛后才提升到 Skill 根目录。
2. **只迁移机制，不迁移表达**：提炼写作机制、决策顺序、语气旋钮和适用边界；不复制独特连续表达、固定署名、金句，不把主题事实、人物、数字写进通用 Skill。
3. **不伪造**：不新增源文没有支持的人物、事实、引语、数字或经历；无原始记录的对话只能转述并标记来源。
4. **单篇特征不升级**：只出现一次的特征保留为 `incidental`，不得作为配额或硬门槛写入规则。
5. **safety 独立于风格**：授权、隐私、版权、事实和合规要求独立管理，不伪装成风格特征；出现阻断时暂停，不用文风掩盖问题。
6. **每轮一个变化**：进化循环每轮只改一条规则；keep 的判据是与当前最佳版本盲评成对比较合计不输（样本对净胜 ≥ 0）、本轮目标指标改善且留出集不退化，否则 revert（口径见 §9）。
7. **诚实标注**：区分实测与 dry run、单篇校准与跨文章验证；报告剩余不确定性比继续堆模板更有价值。

后文提到这些约束时只作引用，不再重复展开。

## 3. 何时使用与模式选择

典型触发请求：提炼作者写作风格/写作 Skill、把文章方法沉淀成 SKILL.md、用 Skill 重写原文并对比打分、评估现有写作 Skill 是否过拟合、从 PDF/公众号/专栏/品牌稿抽象方法论。

不适合触发：没有任何源文、只要求从零写一篇普通文章；只做事实/法律/医学审查；明确要求抄袭、冒充来源作者或伪造原始记录。

按请求意图选择模式：

| 模式 | 触发信号 | 做法 | 产出 |
|---|---|---|---|
| 轻量分析 | 只要"分析风格/提炼方法论"，未要求验证 | Phase 1 全做，跳过工作区脚手架和进化循环 | 文章地图 + 证据台账 + style-profile |
| 单篇校准 | 一篇文章 + 要求重写验证 | 全流程，结论受硬约束 1 限制 | `calibration/` 隔离产物 |
| 多篇提炼 | 多篇文章 + 要求生成 Skill | 全流程，先找跨文章重复机制再按题材分组 | 完整 Skill 目录 |
| 现有 Skill 进化 | 给定旧 Skill + 新样本 | 读取旧 Skill、回归样本、评分日志，进入进化循环 | 变更记录 + 可回滚版本 |
| 仅评估 | 只要评估不要修改 | 生成测试提示和评分卡，不创建、覆盖或回滚文件 | 台账 + 测试提示 + 建议变更 |

默认从轻量分析开始；用户明确要求验证或生成可用 Skill 时才升级到全流程。

评估任务分两种并在测试提示中标注：`same-task` 保留同一写作目的，用来校准源文机制；`transfer` 迁移到新题型或新材料，用来检查泛化。单篇的 `transfer` 只算迁移压力测试，不能替代第二篇独立文章的验证。

## 4. 输入契约

先确认并记录：

- 样本文件、数量、格式和是否能读取全文；PDF 需抽查页面视觉结构，不能只依赖 OCR；
- 目标任务：仿写、改稿、内容生产、品牌统一，还是仅做风格研究；
- 目标读者、发布渠道、语言、长度和必须保留的事实；
- 来源文章的使用授权、作者身份和隐私边界；没有授权时只提炼抽象机制，不替来源作者发声；
- 样本跨越多年时，作者风格是否随时期变化，默认采用哪个时期的声音（跨时期共性进核心，时期特征做旋钮）；
- 用户希望的输出位置。未指定时，在当前工作区建立独立 Skill 目录，不覆盖现有 Skill。

全流程开跑前告知预计成本（子 agent 数量见 `references/evaluation-rubric.md` §8.4）。

## 5. Phase 0：工作区（仅全流程模式）

注意区分两套目录：下面是**你要生成的目标 Skill** 的布局，不是本 Skill 自身的文件。

```text
<skill-dir>/
├── SKILL.md                         # 只放核心流程与触发描述（<500 行）
├── agents/openai.yaml               # 可选：按仓库惯例提供 UI 元数据
├── references/style-profile.md      # 稳定机制与条件规则
├── evals/evaluation-rubric.md       # 评分维度、门槛和自动失败项（训练层，生成器不读）
├── evals/test-prompts.json          # 测试输入、字数口径与期望行为
└── reports/                         # evidence-ledger、evolution-log、evolution-report、results.tsv、runs/
```

机械预检使用本 Skill 自带的 `scripts/precheck.py`，不需要复制到目标 Skill。每个版本的 Skill 快照、任务文件、稿件和评审结果放在 `reports/runs/<版本>/`，回滚时从快照恢复。

若环境有 git，先创建工作分支并记录基线；没有 git 时用带时间戳的备份。绝不使用破坏性 reset 覆盖用户已有改动。

设计 2—3 个测试提示（多题型时每个题型至少一个）：至少一个典型场景、一个不同题型或更复杂场景；单篇时测试提示必须覆盖同一机制的不同表达，不能只换名词。提示中只写任务和输入材料，不泄露期望答案或准备修复的规则。每个提示写明字数范围和计数口径 `length_unit`；至少一个提示的素材包含作者提供的真实经历片段，否则“场景与作者在场”无法在不补造的前提下被测出来。素材体量要撑得起字数下限：素材只够 400 字却要求 800 字，写手会扩写经历、补感想句来凑字，测出来的编造来自测试设计而不是 Skill（字段见 `references/evaluation-rubric.md` §4）。默认把测试提示展示给用户后**继续执行**，用户可随时否决调整；仅当用户要求逐步确认时才阻塞等待。

## 6. Phase 1：从文章提炼证据

先登记语料缺陷（截断、OCR 断行、笔误、平台栏位），避免把缺陷学成风格；样本多到单个 agent 读不完时，按题材或时期分组并行提炼再合并。做法见 `references/evidence-and-scope.md` §2.2、§2.3。

### 6.1 文章地图

逐篇记录以下事实，使用短语和转述，不复制长段落：

1. 文章任务：解释、说服、复盘、叙事、建信任、销售转化或其他；
2. 读者问题与核心冲突：读者起初相信什么，作者让其改变了什么判断；
3. 结构因果：事件/问题如何进入，哪条证据改变了决策，结尾如何收束；
4. 语言行为：人称、句长、段落节奏、问答、术语解释和视觉重音；
5. 证据与场景：数字、对话、物件、动作、情绪分别承担什么功能；
6. 交易与安全：哪些事实必须保留，哪些只能转述、泛化或删除。

### 6.2 证据台账

每条候选规则按 `references/evidence-and-scope.md` §2 的台账格式记录一行，保存为独立的 `reports/evidence-ledger.md`，不能只留在临时推理中。观察分为 `invariant` / `conditional` / `incidental` / `safety` 四类，分类判据和晋级条件见同文件 §1、§3。

把规则写成可执行动作（"先呈现读者的具体疑问，再给方向性判断"），不写空泛形容词（"要有作者感"），不用"像不像作者"作为唯一观察。

每条规则必须填 `fallback`：素材不足时怎么降级。需要具体内容才能执行的动作（自评限定、回指缺口、验收标准、禁令式结尾、分人群建议）缺素材时一律“跳过该动作”，否则模型会为了完成动作而补造（`references/evidence-and-scope.md` §2.1）。反例检查发现某动作只在一种子题型出现时（如叙事型复盘有、记录型复盘没有），把规则拆成按素材判定的两种写法，而不是写成该题型的必做动作。

## 7. Phase 2：生成最小可用 Skill

先写一个能完成任务的最小版本，再加入经过验证的例外。目标 Skill 分成**运行时层**与**训练生命周期层**：运行时 `SKILL.md` 只负责稳定地产出内容；证据台账、评分、回归、接受和回滚规则放在 `evals/` 与 `reports/`，不要挤占运行时上下文。

运行时 `SKILL.md` 必须包含：

1. frontmatter 中清楚写明"做什么"和"何时触发"；
2. 写作前读取 `references/style-profile.md` 的明确指令；
3. 输入检查与授权/版权边界；
4. 用户任务契约：必须保留的事实、目标读者、长度、格式和禁区；显式任务约束永远高于学到的风格规则；素材撑不到字数下限时贴近下限交付并在交付说明里写明，不扩写素材来凑字；
5. 文章模式选择或题材路由；
6. 从材料到草稿的线性工作流；
7. 事实、引语、数字和推断的证据门槛；
8. 交付前硬约束自检，至少复核长度、必备事实、禁止新增项（含目标、承诺、验收标准、作者决定）和输出格式；
9. 默认输出和失败时的报告格式；
10. 题型动作缺素材时跳过、不补写的条款，以及 §7.1 的素材追问步骤。

把跨样本机制、条件规则、语气旋钮、反模式和风格自检写入 `references/style-profile.md`；长例子与评分表另放 references。不得引用并未生成的文件。不要强迫每篇文章使用相同的开头、编号、小标题、数字、反问、CTA 或免责声明——表层特征默认是旋钮，不是配额。

style-profile 里关于“怎么写”的元规则（如“类比只用一次”）要写成对写手的指令，并在反模式里注明“不要在正文里说出这条规则”；否则模型会把方法用语写进正文。

### 7.1 素材追问

作者文章里的现场感、情绪和“不吐不快”，来自真实经历；写法规则补不出来，硬补就是编造。目标 Skill 的工作流必须包含：

1. 写作前检查素材里有没有作者亲历的具体时刻（在哪、做了什么、当时什么反应）；
2. 没有、而题型需要时（评测、随笔、观点文），先向作者追问 1—2 个真实时刻，问题要具体（“第一次听出这个差别时，你在听哪首、在什么环境？”）；
3. 作者不提供或无法追问时，按素材写，并在交付说明中写明“缺少现场素材”，不得自行补写场景、动作或情绪。

测试时用含经历片段的提示验证这一步（见 Phase 0）。

## 8. Phase 3：基线、重写与盲评

在看到重写结果前，先固定评分口径：维度、权重、通过线和自动失败项见 `references/evaluation-rubric.md`。评分的是机制和读者效果，不是字面相似度。

对每个测试提示保留三份材料：`source`（原文或事实基线）、`baseline`（不加载 Skill 的完成稿）、`candidate`（加载候选 Skill 的完成稿）。

**评分卡用于诊断，成对比较用于裁决。** 单次 LLM 绝对打分噪声大（±1 分以上），不作为 keep/revert 依据；评分卡的作用是定位最低分维度、指出下一轮该改什么。裁决用盲评成对比较：评审只接收源文、用户任务和两份匿名稿件（不知道哪份是新版本），回答哪份更好地完成任务、是否保留结构机制与声音、是否引入模板化/虚构/版权风险。

每个版本在每个提示上至少生成 2 篇（各自独立的生成 agent），按样本配对盲评，单样本的胜负常被与改动无关的生成波动决定（配对与合并规则见 `references/evaluation-rubric.md` §8.2）。有条件时用独立子 agent 盲评，生成和评审 prompt 用 `references/agent-prompts.md` 的固定模板；没有时可以干跑（同一上下文生成并评审，不盲，只出诊断，不出胜负），但必须标记 `eval_mode: dry_run`，不把干跑当实测。自动失败由编排者对照原文复核后才计入；双方都自动失败的样本对记 tie，两边各计一篇失败稿。

盲评前先跑机械预检 `scripts/precheck.py`（字数、素材外数字与书名、语料重合），评审不自行计数；盲评材料准备（去掉交付说明、随机 X/Y、交换顺序、隐藏映射、固定 JSON 输出）按 `references/evaluation-rubric.md` §8 执行。生成器只读 Skill 和任务文件，永远不读留出集；留出原文可以给评审作口吻参考。

每个 win 记录胜因：`quality` 或 `opponent_fail`（对手触发自动失败）。主要靠对手失败取胜时，只能说明 Skill 减少了失误，不能说明它提升了写作质量。

同时区分过程评分（是否完成文章地图、台账、测试设计、日志）与输出评分（稿件质量）；只有输出在多个提示和留出集上改善，才能说明候选 Skill 有效。

## 9. Phase 4：受控自进化循环

默认最多 3 轮，v1 对 baseline 计为第 1 轮；每轮严格执行：

```text
先看自动失败项（编造、泄漏等），有就先修它；没有再用评分卡诊断最低分维度
→ 提出一个具体规则变化，写明预期机制（为什么会改善、改善哪个维度）
→ 只修改该维度相关的 Skill 内容
→ 同一测试集重写，盲评成对比较新旧版本
→ 检查 holdout、自动失败项和模板坍缩
→ 按生成前写定的口径裁决：净胜不为负、无提示明确退化、目标指标改善则 keep，否则 revert
```

比较对象：v1 与 baseline 只比一次，作为“Skill 是否有用”的门槛；之后每轮与**当前最佳版本**比较。keep 口径（样本对合计净胜 ≥ 0、无提示两对都 lose、留出净胜 ≥ 0、目标指标改善）和“预期受影响的提示 id”在生成候选稿之前写进进化日志，见 `references/evaluation-rubric.md` §3.6；同时报告交换顺序不一致率，每个 run 做一次 A/A 对照估噪声底（§3.8）。

每轮记录：改了哪条规则、基于哪些证据、预期机制、盲评结果、是否影响其他题型、keep/revert 及原因、**预测是否命中**。命中的判据事先写定：目标是失误类时，看稿件计数是否下降；目标是质量维度时，看该维度的 `dimension_winners` 在全部样本对上是否 win 多于 lose。不用评分卡绝对分判定命中，否则停机会被噪声触发。

停机诊断后的“源头修订”也按一处一轮验证。一次改多处，结果有好有坏时无法归因，只能事后拆解（一次真实训练里的教训）。

### 9.1 预测校准停机

累计追踪每轮"预期 vs 实际"。连续两轮预测失败（预期改善的维度没有改善，或改善出现在别处），说明对问题的因果模型是错的——立即停止爬山，回到 Phase 1 重新诊断，而不是继续换规则试。这条早于"连续两轮无改善"触发。

单轮预测失败时，下一轮先回到台账检查规则的证据范围和 `negative_case`，而不是在原假设上追加约束。常见情形：补造问题的根因多半是某条规则的适用范围过宽，加一句笼统的“不要补写”通常无效。

### 9.2 禁止的刷分方式

- 为某篇文章新增人物、金额、句子或事实；
- 把评审指出的一个句子硬编码为通用模板；
- 只增加免责声明、CTA 或编号来掩盖结构问题；
- 为了提高“现场感”“张力”等维度，让写手制造素材里没有的冲突、场景或作者决定（这类维度缺素材时走 §7.1 素材追问）；
- 同时改多个维度，导致无法归因；
- 让验证样本参与规则提炼后，再声称它证明了泛化。

连续两轮最低维度没有改善时，停止局部加规则并报告瓶颈；用户确认后才做一次探索性重写，探索性重写也必须与当前最佳版本盲评比较，失败则恢复。

### 9.3 裁判审计（外环）

rubric 在单个 run 内冻结。案例主要来自作者校准（`references/evaluation-rubric.md` §3.8）：作者匿名选出的稿件与评审裁决不一致时登记。run 结束后，若出现"评分结论与用户实际判断相悖"的案例（高分稿用户觉得差，或反之），记入 rubric 缺陷日志；累积 2 个以上指向同一缺陷的案例后，才允许在**下一个 run 开始前**修改一次 rubric，且 rubric 自身保留 changelog 和可回滚版本。永远不在进化循环进行中修改评分标准。

## 10. Phase 5：回归、防过拟合与停止

### 10.1 回归设计

- 3 篇以上：测试提示至少覆盖 2 种题型；
- 2 篇起就要留出（篇数门槛只在 `references/evidence-and-scope.md` §4.1 陈述一次），不只在原文上自测；模板坍缩检查见同文件 §4.2；
- 不同题型允许不同结构：检查家庭故事是否被改成清单、服务文章是否被改成广告、概念文是否被强行塞进人物故事。

### 10.2 通过、加压与停止

通过条件：无自动失败项、达到 rubric 门槛，且结构、声音、泛化维度不明显低于其他维度（具体数值见 `references/evaluation-rubric.md` §2）。

候选在全部测试提示和留出集上通过后，不直接宣布完成：生成一个更难的 `transfer` 提示（新题型或更复杂材料），经用户确认后作为附加压力测试，防止"测试太软"造成的虚假通过。压力测试失败不回滚已通过版本，只写入遗留风险。

遇到以下情况立即暂停：源文不可读、授权不明、关键事实无法核验、候选稿新增不可追溯引语/数字、版权或身份冒充风险、验证集明显退化。

达到门槛、触发 §9.1 停机、或已证明新增规则只对单篇有效时停止。停止不是失败。

## 11. 交付

按模式交付，用户要求时删减：

1. 已验证：可直接使用的 `SKILL.md`（含仓库惯例要求的 `agents/openai.yaml`）；单篇：`calibration/draft-SKILL.md`（硬约束 1）；
2. `references/style-profile.md`、`evals/evaluation-rubric.md`、`evals/test-prompts.json`；
3. `reports/evidence-ledger.md`、`reports/evolution-report.md`、可选 `reports/results.tsv`；
4. 轻量分析模式只交付文章地图、证据台账和 style-profile。

报告第一行写：`状态：已验证 / 暂定（单篇校准） / 暂停（待授权、待事实、待测试或待用户确认）`

## 12. 异常处理

- 只有一篇文章：按硬约束 1 处理，附第二篇测试建议；
- PDF/OCR 不完整：标记不可见段落，不猜测缺失文字；需要视觉判断时先读取 PDF 相关 Skill；
- 没有 git：创建可恢复备份，报告无法执行 commit/revert；
- 子 agent 不可用：dry run 并降低置信度；
- 盲评胜出但 holdout 下降：判为过拟合，拒绝该修改；
- 用户要求单篇结果直接上线：说明这是同文校准，未通过第二篇独立迁移测试前不把 `draft-SKILL.md` 改名为可加载的 `SKILL.md`；
- 用户只要 Skill 不要文章：交付规则和验证资产，不擅自生成完整仿写稿。

## 13. 快速自检

- 是否把"观察"与"规则"分开，每条核心规则有台账证据和 `fallback`？
- 测试提示是否写明 `length_unit`，是否至少一个提示含作者真实经历片段，素材体量是否撑得起字数下限？
- 每个版本每个提示是否至少 2 个样本，并按 rubric §8.2 配对合并？
- 盲评前是否跑过 `scripts/precheck.py`，评审是否按 rubric §8 协议拿到去标识、交换顺序的材料？
- 每轮比较对象和 keep 口径是否在生成前写进日志？胜场是否区分 `quality` 与 `opponent_fail`？
- 硬约束 1—7 是否全部满足？
- 是否先固定评分口径再看候选稿？keep/revert 是否基于盲评成对比较而非单次绝对分？
- 每轮是否只改一个维度，预测命中是否被追踪？
- 是否有 baseline、candidate 和至少一个不同题型/留出样本？
- Skill 本体是否少于 500 行，长资料是否放在 references？

详细规范见：

- `references/evidence-and-scope.md`：证据台账格式、规则晋级和防过拟合（Phase 1、5 时读取）；
- `references/evaluation-rubric.md`：评分卡、测试提示模板、比较口径、进化日志、裁判审计、机械预检与盲评协议（Phase 0、3、4 时读取）；
- `references/agent-prompts.md`：生成器和评审的固定 prompt 模板（Phase 3、4 时读取）；
- `scripts/precheck.py`：盲评前的机械预检（Phase 3）。
