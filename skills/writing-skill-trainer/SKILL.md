# Writing Skill Trainer

## 1. 目标与核心闭环

把给定文章或文章集合，转化为一个可复用、可验证、可回滚的写作 Skill。全流程闭环：

`样本观察 → 证据台账 → 最小 Skill → 测试提示 → 基线重写 → 盲评比较 → 只修最低维度 → 回归验证 → 接受或回滚`

这里的"自进化"是受约束的 hill-climbing：每轮只允许一个可解释的规则变化，盲评胜出且无副作用才晋级。改进对象分两层——内环迭代候选 Skill（按轮），外环审计评分标准本身（按 run，见 §9.3）；两层永远不在同一轮内同时改动。

## 2. 硬约束

以下规则贯穿全流程，只在此处完整陈述一次：

1. **单篇即暂定**：样本少于 3 篇时，所有新规则标记 `provisional`；产物放入隔离的 `calibration/` 目录（`draft-SKILL.md`），不生成可被自动发现加载的 `SKILL.md`，不生成 UI 元数据。达到多篇晋级门槛后才提升到 Skill 根目录。
2. **只迁移机制，不迁移表达**：提炼写作机制、决策顺序、语气旋钮和适用边界；不复制独特连续表达、固定署名、金句，不把主题事实、人物、数字写进通用 Skill。
3. **不伪造**：不新增源文没有支持的人物、事实、引语、数字或经历；无原始记录的对话只能转述并标记来源。
4. **单篇特征不升级**：只出现一次的特征保留为 `incidental`，不得作为配额或硬门槛写入规则。
5. **safety 独立于风格**：授权、隐私、版权、事实和合规要求独立管理，不伪装成风格特征；出现阻断时暂停，不用文风掩盖问题。
6. **每轮一个变化**：进化循环每轮只改一条规则；keep 的判据是盲评成对比较胜出且留出集不退化，否则 revert。
7. **诚实标注**：区分实测与 dry run、单篇校准与跨文章验证；报告剩余不确定性比继续堆模板更有价值。

后文提到这些约束时只作引用，不再重复展开。

## 3. 何时使用与模式选择

典型触发请求：提炼作者写作风格/写作 Skill、把文章方法沉淀成 SKILL.md、用 Skill 重写原文并对比打分、评估现有写作 Skill 是否过拟合、从 PDF/公众号/专栏/品牌稿抽象方法论。

不适合触发：没有任何源文、只要求从零写一篇普通文章；只做事实/法律/医学审查；明确要求抄袭、冒充来源作者或伪造原始记录。

按请求意图选择模式：

| 模式 | 触发信号 | 做法 | 产出 |
|---|---|---|---|
| 轻量分析 | 只要"分析风格/提炼方法论"，未要求验证 | Phase 1 全做，跳过工作区脚手架和进化循环 | 文章地图 + 证据台账 + style-profile |
| 单篇校准 | 一篇文章 + 要求重写验证 | 全流程，结论受硬约束 1 限制 | `calibration/` 隔离产物 |
| 多篇提炼 | 多篇文章 + 要求生成 Skill | 全流程，先找跨文章重复机制再按题材分组 | 完整 Skill 目录 |
| 现有 Skill 进化 | 给定旧 Skill + 新样本 | 读取旧 Skill、回归样本、评分日志，进入进化循环 | 变更记录 + 可回滚版本 |
| 仅评估 | 只要评估不要修改 | 生成测试提示和评分卡，不创建、覆盖或回滚文件 | 台账 + 测试提示 + 建议变更 |

默认从轻量分析开始；用户明确要求验证或生成可用 Skill 时才升级到全流程。

评估任务分两种并在测试提示中标注：`same-task` 保留同一写作目的，用来校准源文机制；`transfer` 迁移到新题型或新材料，用来检查泛化。单篇的 `transfer` 只算迁移压力测试，不能替代第二篇独立文章的验证。

## 4. 输入契约

先确认并记录：

- 样本文件、数量、格式和是否能读取全文；PDF 需抽查页面视觉结构，不能只依赖 OCR；
- 目标任务：仿写、改稿、内容生产、品牌统一，还是仅做风格研究；
- 目标读者、发布渠道、语言、长度和必须保留的事实；
- 来源文章的使用授权、作者身份和隐私边界；没有授权时只提炼抽象机制，不替来源作者发声；
- 用户希望的输出位置。未指定时，在当前工作区建立独立 Skill 目录，不覆盖现有 Skill。

## 5. Phase 0：工作区（仅全流程模式）

注意区分两套目录：下面是**你要生成的目标 Skill** 的布局，不是本 Skill 自身的文件。

```text
<skill-dir>/
├── SKILL.md                         # 只放核心流程与触发描述（<500 行）
├── agents/openai.yaml               # 可选：按仓库惯例提供 UI 元数据
├── references/style-profile.md      # 稳定机制与条件规则
├── references/evaluation-rubric.md  # 评分维度、门槛和自动失败项
├── evals/test-prompts.json          # 测试输入与期望行为
└── reports/                         # evidence-ledger、evolution-report、results.tsv
```

若环境有 git，先创建工作分支并记录基线；没有 git 时用带时间戳的备份。绝不使用破坏性 reset 覆盖用户已有改动。

设计 2—3 个测试提示：至少一个典型场景、一个不同题型或更复杂场景；单篇时测试提示必须覆盖同一机制的不同表达，不能只换名词。提示中只写任务和输入材料，不泄露期望答案或准备修复的规则。默认把测试提示展示给用户后**继续执行**，用户可随时否决调整；仅当用户要求逐步确认时才阻塞等待。

## 6. Phase 1：从文章提炼证据

### 6.1 文章地图

逐篇记录以下事实，使用短语和转述，不复制长段落：

1. 文章任务：解释、说服、复盘、叙事、建信任、销售转化或其他；
2. 读者问题与核心冲突：读者起初相信什么，作者让其改变了什么判断；
3. 结构因果：事件/问题如何进入，哪条证据改变了决策，结尾如何收束；
4. 语言行为：人称、句长、段落节奏、问答、术语解释和视觉重音；
5. 证据与场景：数字、对话、物件、动作、情绪分别承担什么功能；
6. 交易与安全：哪些事实必须保留，哪些只能转述、泛化或删除。

### 6.2 证据台账

每条候选规则按 `references/evidence-and-scope.md` §2 的台账格式记录一行，保存为独立的 `reports/evidence-ledger.md`，不能只留在临时推理中。观察分为 `invariant` / `conditional` / `incidental` / `safety` 四类，分类判据和晋级条件见同文件 §1、§3。

把规则写成可执行动作（"先呈现读者的具体疑问，再给方向性判断"），不写空泛形容词（"要有作者感"），不用"像不像作者"作为唯一观察。

## 7. Phase 2：生成最小可用 Skill

先写一个能完成任务的最小版本，再加入经过验证的例外。目标 Skill 分成**运行时层**与**训练生命周期层**：运行时 `SKILL.md` 只负责稳定地产出内容；证据台账、评分、回归、接受和回滚规则放在 `evals/` 与 `reports/`，不要挤占运行时上下文。

运行时 `SKILL.md` 必须包含：

1. frontmatter 中清楚写明"做什么"和"何时触发"；
2. 写作前读取 `references/style-profile.md` 的明确指令；
3. 输入检查与授权/版权边界；
4. 用户任务契约：必须保留的事实、目标读者、长度、格式和禁区；显式任务约束永远高于学到的风格规则；
5. 文章模式选择或题材路由；
6. 从材料到草稿的线性工作流；
7. 事实、引语、数字和推断的证据门槛；
8. 交付前硬约束自检，至少复核长度、必备事实、禁止新增项和输出格式；
9. 默认输出和失败时的报告格式。

把跨样本机制、条件规则、语气旋钮、反模式和风格自检写入 `references/style-profile.md`；长例子与评分表另放 references。不得引用并未生成的文件。不要强迫每篇文章使用相同的开头、编号、小标题、数字、反问、CTA 或免责声明——表层特征默认是旋钮，不是配额。

## 8. Phase 3：基线、重写与盲评

在看到重写结果前，先固定评分口径：维度、权重、通过线和自动失败项见 `references/evaluation-rubric.md`。评分的是机制和读者效果，不是字面相似度。

对每个测试提示保留三份材料：`source`（原文或事实基线）、`baseline`（不加载 Skill 的完成稿）、`candidate`（加载候选 Skill 的完成稿）。

**评分卡用于诊断，成对比较用于裁决。** 单次 LLM 绝对打分噪声大（±1 分以上），不作为 keep/revert 依据；评分卡的作用是定位最低分维度、指出下一轮该改什么。裁决用盲评成对比较：评审只接收源文、用户任务和两份匿名稿件（不知道哪份是新版本），回答哪份更好地完成任务、是否保留结构机制与声音、是否引入模板化/虚构/版权风险。

有条件时用独立子 agent 盲评；没有时可以干跑，但必须标记 `eval_mode: dry_run`，不把干跑当实测。

同时区分过程评分（是否完成文章地图、台账、测试设计、日志）与输出评分（稿件质量）；只有输出在多个提示和留出集上改善，才能说明候选 Skill 有效。

## 9. Phase 4：受控自进化循环

默认最多 3 轮；每轮严格执行：

```text
用评分卡诊断最低分维度
→ 提出一个具体规则变化，写明预期机制（为什么会改善、改善哪个维度）
→ 只修改该维度相关的 Skill 内容
→ 同一测试集重写，盲评成对比较新旧版本
→ 检查 holdout、自动失败项和模板坍缩
→ 盲评胜出且无副作用则 keep，否则 revert
```

每轮记录：改了哪条规则、基于哪些证据、预期机制、盲评结果、是否影响其他题型、keep/revert 及原因、**预测是否命中**（预期改善的维度是否真的改善）。

### 9.1 预测校准停机

累计追踪每轮"预期 vs 实际"。连续两轮预测失败（预期改善的维度没有改善，或改善出现在别处），说明对问题的因果模型是错的——立即停止爬山，回到 Phase 1 重新诊断，而不是继续换规则试。这条早于"连续两轮无改善"触发。

### 9.2 禁止的刷分方式

- 为某篇文章新增人物、金额、句子或事实；
- 把评审指出的一个句子硬编码为通用模板；
- 只增加免责声明、CTA 或编号来掩盖结构问题；
- 同时改多个维度，导致无法归因；
- 让验证样本参与规则提炼后，再声称它证明了泛化。

连续两轮最低维度没有改善时，停止局部加规则并报告瓶颈；用户确认后才做一次探索性重写，探索性重写也必须与当前最佳版本盲评比较，失败则恢复。

### 9.3 裁判审计（外环）

rubric 在单个 run 内冻结。run 结束后，若出现"评分结论与用户实际判断相悖"的案例（高分稿用户觉得差，或反之），记入 rubric 缺陷日志；累积 2 个以上指向同一缺陷的案例后，才允许在**下一个 run 开始前**修改一次 rubric，且 rubric 自身保留 changelog 和可回滚版本。永远不在进化循环进行中修改评分标准。

## 10. Phase 5：回归、防过拟合与停止

### 10.1 回归设计

- 3 篇以上：至少覆盖 2 种题型；5 篇以上：训练集/留出集切分，不只在原文上自测；
- 留出策略与模板坍缩检查的具体做法见 `references/evidence-and-scope.md` §4；
- 不同题型允许不同结构：检查家庭故事是否被改成清单、服务文章是否被改成广告、概念文是否被强行塞进人物故事。

### 10.2 通过、加压与停止

通过条件：无自动失败项、达到 rubric 门槛，且结构、声音、泛化维度不明显低于其他维度（具体数值见 `references/evaluation-rubric.md` §2）。

候选在全部测试提示和留出集上通过后，不直接宣布完成：生成一个更难的 `transfer` 提示（新题型或更复杂材料），经用户确认后作为附加压力测试，防止"测试太软"造成的虚假通过。压力测试失败不回滚已通过版本，只写入遗留风险。

遇到以下情况立即暂停：源文不可读、授权不明、关键事实无法核验、候选稿新增不可追溯引语/数字、版权或身份冒充风险、验证集明显退化。

达到门槛、触发 §9.1 停机、或已证明新增规则只对单篇有效时停止。停止不是失败。

## 11. 交付

按模式交付，用户要求时删减：

1. 已验证：可直接使用的 `SKILL.md`（含仓库惯例要求的 `agents/openai.yaml`）；单篇：`calibration/draft-SKILL.md`（硬约束 1）；
2. `references/style-profile.md`、`references/evaluation-rubric.md`、`evals/test-prompts.json`；
3. `reports/evidence-ledger.md`、`reports/evolution-report.md`、可选 `reports/results.tsv`；
4. 轻量分析模式只交付文章地图、证据台账和 style-profile。

报告第一行写：`状态：已验证 / 暂定（单篇校准） / 暂停（待授权、待事实、待测试或待用户确认）`

## 12. 异常处理

- 只有一篇文章：按硬约束 1 处理，附第二篇测试建议；
- PDF/OCR 不完整：标记不可见段落，不猜测缺失文字；需要视觉判断时先读取 PDF 相关 Skill；
- 没有 git：创建可恢复备份，报告无法执行 commit/revert；
- 子 agent 不可用：dry run 并降低置信度；
- 盲评胜出但 holdout 下降：判为过拟合，拒绝该修改；
- 用户要求单篇结果直接上线：说明这是同文校准，未通过第二篇独立迁移测试前不把 `draft-SKILL.md` 改名为可加载的 `SKILL.md`；
- 用户只要 Skill 不要文章：交付规则和验证资产，不擅自生成完整仿写稿。

## 13. 快速自检

- 是否把"观察"与"规则"分开，每条核心规则有台账证据？
- 硬约束 1—7 是否全部满足？
- 是否先固定评分口径再看候选稿？keep/revert 是否基于盲评成对比较而非单次绝对分？
- 每轮是否只改一个维度，预测命中是否被追踪？
- 是否有 baseline、candidate 和至少一个不同题型/留出样本？
- Skill 本体是否少于 500 行，长资料是否放在 references？

详细规范见：

- `references/evidence-and-scope.md`：证据台账格式、规则晋级和防过拟合（Phase 1、5 时读取）；
- `references/evaluation-rubric.md`：评分卡、测试提示模板、进化日志和裁判审计格式（Phase 3、4 时读取）。
